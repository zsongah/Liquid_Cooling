## 2. 产品定位、模块和上下游

可先看 [当前实施框架 PNG](assets/aidc-implementation-overview.png) 与 [代码和通信链路 PNG](assets/aidc-control-dataflow.png)。[双图查看页](实施框架与通信链路.html) 提供可放大的 SVG。两图对应 v0.6.0，包含工作台、配置发布、预测前馈与多独立域；界面使用方法见第 8.3–8.4 节。图中绿色表示候选与下发，蓝色表示采集与回读；实际模块调用由 Engine 编排。FMU 走独立实验适配路径，不经过现场 Modbus 网口。文件名带 `-v04` 的原图仍是 v0.4.1 历史快照。

软件接收配置、设备观测和可选负荷预测，计算 CDU 监督层目标。CDU 本地 PLC/DDC 继续负责泵阀快速内环、联锁和失联接管。通用性来自统一数据语义、能力声明和独立适配器；不意味着任意品牌仅填 IP 就能控制。

```text
上游：设备点表 / 工程限值 / CDU—机柜—热汇关系 / 可选机柜功率预测
                                  ↓
边缘软件：接入归一 → 数据检查 → 热需求与目标计算 → 命令网关
                         ↑              ↓                 ↓
                         └── 参数校准 ← 数据和决策记录     目标下发
                                                          ↓
下游：CDU 本地控制器 → 泵阀与液冷回路 → 运行反馈 → 接入归一

外部 BMS / iCooling / 冷源群控：先明确控制权与协调接口
当前未实现这些平台的专用连接器或多 CDU / 冷站协调器
```

| 模块 | 已实现 | 当前边界 |
|---|---|---|
| 配置与拓扑 | 资产父子关系、供回端口与连接、热汇、共享关系、能力检查、设备布局与配置版本 | 图可表达的关系不代表已经具备相应水力求解和协调策略 |

| 控制 | 热需求计算、正温差反馈、流量或压差目标 | 自动策略保持供温，不直接调泵频，不做全站总能耗寻优 |
| 外部功率预测 | 发布版本绑定的 HTTP 输入、节点/机柜去重聚合、有效期/时钟校验、每周期前馈和使用审计 | 不生成上游预测；只调 CDU 聚合目标，没有独立机柜阀门分配 |

## 3. 配置与最小拓扑

示例模板放在 `examples/`，工作台创建的版本保存在 `outputs/workbench/configs/`。软件 v0.6.0 与配置版本 "0.1" 是两个概念；不要把 schema_version 改为软件版本。旧配置保持兼容，新增字段为可选。配置经统一校验后建立适配器。现场模板空地址及占位 IP 会故意导致校验失败，其余数值也只是示例。

`experiments/fmu_validation_matrix.json` 是 FMU 多工况实验编排配置，不能传给场景 `validate`；由 `tools/run_fmu_validation_matrix.py --matrix` 读取。批量检查场景时逐个调用 `validate`，将 `field_template.UNBOUND.json` 作为预期失败的负例。原始运行 `.log` 默认由 Git 忽略但保留在本地；需要版本管理的验证结果应作为明确命名的报告单独评审。

| 配置位置 | 内容 | 对核心的影响 |
|---|---|---|
| 根字段 | schema_version、scene_id、topology_version、provenance、notes | 版本与来源；拓扑版本参与命令检查 |
| assets | 稳定 id、kind、label、parent_id；可登记机柜内 node 和管网部件 | 校验引用与父子关系；增加资产不自动增加实测或模型 |
| control_domains | id、cdu_id、owner、heat_sink_id、served_racks、shared_hydraulics | 选择对象、归属、预测聚合范围及共享控制限制 |
| devices[id].type / adapter | liquid_to_liquid 或 liquid_to_air；mock、thermal_sim、modbus_tcp、sustain_fmu | 选择热汇检查和适配器；FMU 走专用实验入口 |
| connection / points | 网络、超时、标准量与设备点位绑定 | 通信、解码、单位及状态语义 |
| controls | unit、minimum、maximum、max_step、minimum_interval_s、allowed_modes | 可写能力与动作约束 |
| guards / max_data_age_s | 观测工程上下限、允许数据年龄 | 异常阻止优化，进入暂停/接管流程 |
| policy | 比热、流量范围、温差、回温软限值、水力先验、时域、校准开关 | 需求计算、预测和晋升条件 |
| write_enabled / commissioning | 点表/限值确认、唯一控制权、设备看门狗、本地接管、证据引用 | 真实控制门槛；配置勾选不是自动认证 |
| initial_setpoints / initial_observations / simulation | 仿真初值、对象参数 | 仅用于开发对象，不能冒充实测 |
| extensions | 厂家/固件、文档、工程标签等元数据 | 普通核心不自动执行；FMU 工具专门读取 sustain_fmu_experiment |
| physical_topology | evidence、ports、connections、layout | 供回连接与回路侧别校验、物理连接展示；不求解管网 |
| policy.kind | 已注册策略标识；缺省 flow | 策略工厂选择，目前内置为原有 FlowPolicy |

**可登记并展示机柜、节点和明确的供回管连接。** 当前执行器仍为每台 CDU 一个域，CLI/每个工作台任务选择一个域；独立域可以建立各自任务。served_racks 决定哪些机柜预测汇总到该 CDU，物理图与服务关系需一致。没有 physical_topology 的旧场景只显示“服务关系”，不画成已核验的水管。液对液/液对气类型不决定压差/流量控制，实际可写能力才决定。

普通现场网关在 shared_hydraulics=true 时拒绝单域自动控制。不能为绕过检查把共享回路填成独立。目前没有跨域冗余供液、支路压降求解或机柜最小流量分配；FMU 的受限实验例外见第 9 节。

拓扑、工质、设备或策略变更后应重查参数与边界。模型恢复绑定完整场景哈希，改变配置不直接继承旧模型。界面支持草稿编辑、校验与发布，已运行会话保持原快照；启用新版本需要新会话，尚不支持热更新控制参数。拖动画布只改布局，不改管路或实际设备。向 extensions 增加字段不会自动增加物理算法。

physical_topology.ports 的每个端口包含 id、asset_id、side（primary/secondary）、direction（supply/return）、loop_id；这里 direction 表示供回用途。connections 使用 id、from_port、to_port 明确连接。板换两侧禁止以液路边直连；供回管分别声明，不能把供回短接。evidence 为 illustrative/declared/verified，verified 还需 evidence_reference；软件只核对声明完整性，不替现场认证。layout 为资产 ID 到 {x,y} 的映射；仅服务图的布局存于 extensions.ui_layout。

可达性按“资产＋loop_id”检查，同一设备上的不同水路不会被隐式连通。每个服务对象必须具有同回路可达的供液与回液路径，不要求供回管一定直连同一对资产。`examples/workbench_split_headers.json` 包含分开的供液/回液总管和配置态平衡阀；阀门没有驱动绑定，不会因此获得独立控制能力。液对气 CDU 的空气热汇不能被画成一次侧水管。

## 4. 观测量、控制量与设备点表

| 标准量 | 内部单位 | 来源与用途 |
|---|---|---|
| cdu.sec_supply_temp / cdu.sec_return_temp | K | 二次供回液实测温度，热需求与保护检查 |
| cdu.sec_flow | kg/s | 二次质量流量，控制和水力校准 |
| cdu.sec_dp | kPa | 实际供回差压；不能用目标值或单点绝压冒充 |
| cdu.liquid_load | W_th | 可选独立液冷热负荷；缺失时由流量/温差反算 |
| cdu.electric_power | W_e | 可选电功率；需明确泵、整机或其他计量边界 |
| cdu.sec_supply_temp_sp | degC | 供液目标；自动策略保持，不寻优 |
| cdu.dp_sp / cdu.sec_flow_sp | kPa / kg/s | 自动策略二选一输出的目标及回读 |
| cdu.pump_speed_rel | 1 | 契约支持，当前 FlowPolicy 不输出泵速 |
| status.mode / owner / alarm | 设备枚举/状态 | 实际模式、归属和告警；未知不视为正常 |
| status.sample_counter | 设备计数 | 可选源停更检测；无真实计数不能证明传感器刷新 |

点表分 observations、setpoints、status、commands。绑定提供零基 address、read_function、dtype、unit；按需提供 byte_order、word_order、scale、offset、invalid_raw。设定量另需 write_function、tolerance，可用 write_address 区分写地址；当前读写共用编码与换算。

实现 FC01/02 单个位读取、FC03/04 寄存器读取、FC06/16 寄存器写入，以及 16/32 位有符号/无符号整数、Float32、布尔位。未实现 FC05/15 线圈写入、位域读改写、多步提交握手或延迟确认状态机。异步更新目标的设备应扩展适配，不能仅扩大回读容差掩盖失败。

- OEM 可能使用 40001 或一基编号；确认表示方式后转换为 PDU 零基地址，不能一律减 40001。
- °C 温度观测用 offset=273.15 转 K；温度设定仍为 °C。
- L/min 流量按实际密度换算：kg/s = L/min × density_kg_m3 / 60000。工质比热和密度都要有依据，不自动假定为纯水。
- 网络新回包不等于 PLC/传感器新采样。源计数器检查停更，不能替代传感器校准。
- setpoint_confirmed 表示目标回读一致；实际温度、流量、压差响应需单独看观测。

只读配置允许 controls={}。无写点、模式/归属不明或告警不可用时，不能宣称控制就绪。`examples/modbus_emulator.json` 地址为虚构，不能用于硬件。

## 5. 控制与在线校准

当前是有界规则控制，先计算液冷热需求，再调流量或压差。没有深度学习控制器，也没有以总冷却能耗为目标的优化求解。

```text
热负荷 Q = 独立液冷热负荷（若有）
         或 cp × 实测质量流量 × (回液温度 − 供液温度)
需求热量 = max(当前热负荷, 有效外部预测峰值)
可用温差 = min(目标温差, 回温软限值 − 当前供温)
需求流量 = 需求热量 / (cp × 可用温差) + 正温差超差反馈

流量模式：目标 = 有界需求流量
压差模式：稳态压差 = (有界需求流量 / gain)^(1/exponent)
          候选 = 稳态压差 + dp_feedback_gain × (稳态压差 − 实测压差)
再经设备范围、单次幅度、死区、最短间隔和命令网关检查
```

无效数据、告警、供温超过策略回温软限值等条件会阻止正常优化。需求超能力记录容量不足，不能通过不断增大目标保证超出设备容量的需求。

一阶回温预测使用配置 thermal_tau_s 与 horizon_s。如果负荷来自同一组当前温差/流量且无独立预测，可能退化为持值预测；低误差不能证明预测有效。

### 5.0 水力模型与实际压差反馈（v0.4.1）

默认通用配置保持旧控制行为；当前 FMU 示例已切换为修正模型。三个 gain 不要混淆：水力 gain 将压差换算成流量；dp_feedback_gain 是新增外环 P 反馈；FMU 本地 PID 的 k 是设备内部参数，本次未修改。

| 参数 | 含义与取值 |
|---|---|
| `hydraulic_model` | 显式给出 `exponent`、`gain`、`gain_bounds` 三个字段；不能与旧 `flow_per_sqrt_kpa` / 顶层 `gain_bounds` 混用 |
| `exponent` | 0.25–1.5 内的固定模型指数；旧模型 0.5；本次 FMU 1.0，不能直接套给其他 CDU |
| `gain` | 单位 kg/s/kPa^exponent；FMU 固定负荷 hold 辨识为 0.0646448823，边界 [0.04, 0.09] |
| `dp_feedback_gain` | 0–2，无量纲，默认 0；只用于压差控制；FMU 取 2。逐步逼近后补偿消退，无积分积累，仍经过限幅限速 |
| `calibration_max_dp_error_kpa` | 可选正数；当前压差未靠近回读目标时清空训练窗口并冻结晋升；FMU 取 0.5 kPa |

反馈默认关闭，现场须按实际阶跃结果整定。反馈可能增加瞬态泵耗，不能由“误差下降”直接推出节能。FMU 示例的指数和初值只来自先前恒定负荷数据，不读取评估时段的未来负荷。修正实验没有触发在线晋升，效果来自事前辨识与反馈。

新增决策记录 `equilibrium_control_target`（模型稳态目标）、`raw_control_target`（含反馈候选）、`bounded_control_target`（限幅）、`limited_control_target`（限速）、`flow_tracking_error_kg_s`、`dp_tracking_error_kpa`、`model_flow_at_min_dp_kg_s` / `model_flow_at_max_dp_kg_s`。实际执行仍以 receipt 与 Master 写入日志为准。记录 `control_rate_limited`、`control_below_minimum`、`feedback_command_clipped` 等原因，保留原需求曲线，不通过改需求假装跟上。

当前上限由 `policy.py` 的 `DP_FEEDBACK_GAIN_BOUNDS = (0.0, 2.0)` 明确限制。2.0 是软件允许整定范围的上界，不是设备物理上限，也不是所有机房的稳定性保证。已有 FMU 矩阵只测试 0、1、2 三个离散值；小幅负荷下 Kp 从 0 增到 2，流量 MAE 由 0.508 增至 0.600 kg/s，泵耗由 3.511 增至 3.633 kWh。增大 gain 不保证更准确或更节能。扩大支持范围前，应补充延迟、噪声、限幅限速和多负荷工况验证；当前不会因单次配置值合法就推荐用于现场。

### 5.1 学习逻辑与参数恢复

只校准 flow ≈ gain × dp^exponent 中的聚合增益，exponent 固定、不在线学习。旧配置仍为平方根模型（exponent=0.5）；参考 FMU 修正配置采用局部辨识的线性模型（exponent=1）。需要正常质量、无告警、准稳态、非执行器边界且有足够压差变化。缺实际压差、异常或明显瞬态时冻结/清理样本，不把目标当测量拟合。

最近最多保存 60 个合格样本，最后 8 个按时间保留验证，训练至少 12 个；至少积累 20 个后，按采样计数每 10 个尝试候选。候选在 gain_bounds 内、单次变化最多 ±2%、验证 MSE 改善超过 2% 才可晋升；adaptive_enabled=false 时仅记录候选。

现场先关闭自动晋升，积累数据再开放。滚动保留窗口可重叠，不替代独立长期验证。学习不会放宽 guards 或 controls。原始数据和晋升写入 SQLite；相同完整配置可恢复已发布参数，重启后拟合窗口重新积累。

**更准确不自动等于更省电或更快。** 直接流量模式不使用该增益换算目标；本轮 FMU 校准后泵电量增加。响应速度、温度和能耗应分别评价。

## 6. 外部机柜功率预测

`run ... --forecast-file forecast.json` 每周期读取文件，生产方用临时文件加原子重命名更新。本节保留 CLI 文件输入格式；v0.6.0 工作台另提供发布版本绑定的 HTTP 接口及节点/机柜输入，见第 8.4 节。两者都是预测消费接口，不生成预测，不内置任务调度连接器。

下面是格式示例，运行时替换为当前 Unix 秒并覆盖有效时域；rack_id 必须匹配所选域 served_racks。

```json
{
  "issued_at": 1800000000,
  "valid_until": 1800000030,
  "unit": "W_e",
  "racks": [
    {"rack_id": "RACK_01", "liquid_fraction": 0.8,
     "samples": [{"at": 1800000000, "power_w": 50000},
                 {"at": 1800000030, "power_w": 60000}]},
    {"rack_id": "RACK_02", "liquid_fraction": 0.8,
     "samples": [{"at": 1800000000, "power_w": 50000},
                 {"at": 1800000030, "power_w": 60000}]}
  ]
}
```

要求机柜完整且唯一、时间网格一致；拒绝缺失、重复、过期、错位、错误单位和非有限值。机柜总电功率乘液冷分担比例后按 CDU 汇总。当前仅用预测峰值增加需求，不用低预测压低已观测热需求。

这里的提前冷却是提前增大流量/压差，没有主动降低供温或命令冷站预冷。收益取决于预测提前量、误差、电到热时延、分担比例与设备响应。OEM liquid_load 若仍由同一温差/流量计算，就不是独立前馈信息。

### 7.1 适配包和联调顺序

适配包对应厂家、型号、控制器/固件和通信文档版本。只变地址、编码、单位和限值可改配置；协议、握手、回退语义变化需要扩展适配器并测试。

1. 确认对象是 CDU、群控 PLC 还是平台，明确目标属主；避免与 iCooling/BMS 同时写同一目标。
2. 从 `examples/field_template.UNBOUND.json` 绑定真实点表、权限和限值，删除不能证实的可选点；保持 write_enabled=false、adaptive_enabled=false。
3. validate 后 monitor，逐点对照设备面板，核对量程、单位、功率边界、告警、模式、属主和源刷新。
4. 实测目标写入/回读/过程响应、手动优先、唯一控制权、本地接管、断网、进程退出和设备重启。
5. 保存 commissioning 证据，再 shadow 与小范围 control；当前 shadow 也检查真实可控模式/归属，只读本地模式使用 monitor。
6. 建立温度、动作、能耗基线，再逐步开放校准；一个型号联通不代表全品牌兼容。

供温写入还需 OEM 防凝露保护证据，或有效露点观测与余量。当前自动算法不调温，通用网关仍检查温度请求。缺少机柜关键温度/流量时，不能推断机柜热安全。

## 8. 运行模式与边缘部署

| 模式 | 行为 |
|---|---|
| monitor | 默认持续采集和记录，不写优化目标 |
| shadow | 生成、校验、记录候选，不写；检查真实模式与归属 |
| control | 满足能力、边界、数据与验收条件后下发目标 |
| paused | 故障内部状态，停止优化并尝试释放；不是 CLI 启动选项 |

### 8.1 本机 TCP 模拟器

```bash
# 终端一：虚构 CDU，仅本机验证
python3 -m lc_control emulator examples/modbus_emulator.json

# 终端二：只读
python3 -m lc_control run examples/modbus_monitor_only.json --steps 3 --output outputs/my-monitor-001

# 重启模拟器后，再执行控制演示
python3 -m lc_control run examples/modbus_emulator.json --mode control --steps 12 --output outputs/my-wire-001
```

模拟器失去心跳 15 秒后回本地，不自动重新授权；长时间监测后做控制需重启模拟器。现场按真实交接流程操作。`tools/wire_demo.py` 封装启动、四周期控制、退出检查，固定输出到 outputs/wire-demo。

### 8.2 Linux 现场部署示例

下列是目标边缘机路径示例，本地未安装服务、没有真实 site.json。先准备运行用户、虚拟环境、程序、核对后的配置及可写数据目录：

```bash
cd /opt/lc-control
.venv/bin/python -m lc_control validate /etc/lc-control/site.json
.venv/bin/python -m lc_control run /etc/lc-control/site.json \
  --mode monitor --steps 0 --interval 5 --output /var/lib/lc-control/site
```

--steps 0 持续运行；--domain 选择域；--forecast-file 传预测文件；--interval 设置循环周期。控制需显式选择。`deploy/lc-control-monitor.service` 是未安装、未在目标机验收的只读示例，不自动重启为控制。

客户端每次交换建立 TCP 连接，没有连接池/批量点读取；有交换超时与整轮扫描期限。按设备刷新与网络时延设置周期，不承诺大规模高频吞吐。host 使用 IP 字面地址。传统 Modbus TCP 无本驱动提供的认证/加密，配置开关也不是权限系统，应在受管理设备网络部署。

正常退出、Ctrl+C、CLI 收到 SIGTERM 均尝试释放。强杀/断电靠设备独立看门狗。同机端点锁不替代跨主机 PLC/BMS 仲裁。

### 8.3 边缘工作台：查看、配置、发布和运行

在 lc-control 目录执行 `python3 -m lc_control serve`，浏览器打开 http://127.0.0.1:8765。服务与设备循环独立于页面，刷新和关闭浏览器不会重复启动或停止任务。终端保持运行；Ctrl+C/SIGTERM 请求后台任务退出并尝试本地接管，进程强杀不保证交接成功。

```text
浏览器工作台 ── 本机 HTTP / JSON ── ConsoleServer
                                      │
                                  Workbench
                         配置版本 │ 后台任务 │ 查询事件
                                  │          ↑
                             Engine ───── SQLite / 审计
                         观测 → 策略 → 安全网关
                                  │
                                Adapter
                   ┌──────────────┴──────────────┐
             ThermalPlant                   Modbus TCP
              内置合成对象                  设备网口 → CDU 本地控制器
```

界面改配置时只调用配置服务；点击启动后，后台从冻结版本创建 Engine。设备目标写入仍必须经过安全网关。浏览器与 CDU 不直接通信，机柜图标也不会因此成为可控执行器。FMU 由专用 Master 独占推进，运行记录可走同一查询和回放界面。

首次使用建议按以下流程操作，无需硬件：

1. 从配置列表选择 `workbench_physical` 模板。该模板含一个 CDU、两个机柜及四个节点，声明供回端口连接，所有数值均为合成试验条件。
2. 查看拓扑并选中 CDU。没有运行数据时显示未采集；机柜和节点只有资产关系，没有凭空生成分支温度或流量。
3. 在配置工作台点击“复制为新草稿”，然后修改名称、算法参数或连接字段，必要时通过高级 JSON 编辑资产、端口与连接。模板与已发布版本只读；画布拖动仅修改布局草稿。
4. 执行配置检查，查看错误、警告与域能力。检查通过只证明当前软件的配置语义成立，不证明设备连通或现场安全。
5. 保存草稿并发布。草稿可反复修改，revision 乐观锁防止旧页面覆盖新修改；发布版本冻结，后续修改应复制为新草稿。发布不会启动设备或改变已有会话。
6. 在运行页选择发布版本、控制域、合成仿真、运行模式和时长。典型开发设置为 300 秒仿真时长、5 秒数值步长、20 倍运行速度；速度只压缩等待，不改变仿真步长。真正推进 ThermalPlant 并调用现有 Engine，不使用随机演示数据。
7. 在“运行与验证”页查看实际温压流和功率，并对照需求与目标；在“控制追踪”页选择一个周期，检查原始建议、限幅、限速、回执和实际响应。结束后记录仍可回放。

高级 JSON 有未应用内容时，常用参数和资产表单会锁定；可以切换页面查看，但需先“应用 JSON 到草稿”或显式“放弃 JSON 修改”再继续编辑，避免两种编辑方式相互覆盖。放弃只恢复到当前本地草稿，不撤销先前已经应用的其他草稿修改。应用 JSON、保存草稿、发布版本是三个不同动作。

运行视图中，所选任务的 CDU 始终使用该任务的遥测和决策，即使缺测也不会借用较新任务的数值。拓扑内其他 CDU 可补充该配置各域的最新记录，详情标出任务、采样时间和历史状态；这些记录不构成同步的全站瞬时状态。

合成热对象仍是 CDU 聚合模型，不能因配置里有机柜节点就宣称完成逐柜热仿真。`workbench_independent_cdus` 展示多个独立控制域，可按域创建独立任务；不具备共享水路或共享冷源容量调度。实际 Sustain FMU 记录可在工作台中回放，新实验继续使用第 9 节专用 Master/Docker 入口；工作台未实现网页启动任意 FMU。

界面必须按数据来源和状态理解：

| 状态或字段 | 正确含义 |
|---|---|
| synthetic_thermal | 合成热工对象的实际运行输出，不是现场数据 |
| sustain_fmu | 保存的 Sustain FMU 会话；仿真时钟不能当真实时间 |
| modbus_network_unverified | 通过网络驱动获取，可能是模拟器；不自动证明真实 CDU |
| shadow | 计算候选并进行网关检查，不写设备 |
| setpoint_confirmed | 设定值回读一致，process_response 仍可能 not_verified |
| paused / stop_requested | 已暂停或请求退出；本地接管是否完成需另看 handoff_confirmed |
| candidate_only / promoted | 候选参数与已晋升参数不同；界面不会把拟合成功当作已应用 |

工作台的现场监测和影子运行仍需按点表绑定真实配置；不会自动扫描网络。网页发起现场 control 默认被服务拒绝。只有管理员使用 `python3 -m lc_control serve --allow-hardware-control` 启动服务，且配置通过原有 commissioned、看门狗周期、唯一控制权、保护与日志检查，才允许申请闭环。该开关不等于现场验收，也不创建缺失的 OEM 保护能力。停止任务表示退出本软件并尝试交还本地控制，不是远程停泵。

默认状态目录为 `outputs/workbench/`：configs 存草稿/发布版本，jobs 存任务元数据，runs 下每个任务有独立 SQLite 与命令审计；forecasts 存当前输入，forecast_archive 保留原始预测及内容哈希。可用 `--state-dir` 指定管理员管理的可写目录；已发布配置通过哈希和版本绑定任务。同一状态目录由实例锁独占，第二次启动会被拒绝，不改写首个服务的任务状态。服务重启后，旧的活动任务标记 interrupted、接管未知，不自动恢复写控制。单服务最多同时运行四个任务；历史目录扫描有上限，事件查询支持分页，目前没有自动留存清理或跨实例协同管理。

HTTP API 仅绑定回环地址，带 Host/同源检查、会话 Cookie、写操作 CSRF、请求体大小限制和固定文件路由。前端不能提交任意 shell 命令、任意文件路径或直接发设备报文。服务没有实现互联网发布、TLS、多人角色与审批系统；需要远程访问时，应由现场经过认证的安全访问通道连接回环服务。

| API | 作用 |
|---|---|
| GET /api/session、/api/catalog | 页面会话、模板、版本、历史和注册能力目录 |
| GET /api/configs/{id} | 读取脱敏配置与兼容性检查结果 |
| POST /api/configs/validate、/api/configs/draft | 检查配置、保存草稿；不访问设备 |
| POST /api/configs/{id}/publish | 校验并冻结版本；不自动运行 |
| POST /api/jobs、GET /api/jobs | 创建受限后台任务、查询运行状态 |
| POST /api/jobs/{id}/stop | 请求退出任务，最终交接结果异步记录 |
| GET /api/configs/{id}/site | 多独立域的真实采集与决策总览，未采集设备保持缺测 |
| GET /api/runs/{id}、/api/runs/{id}/events | 查询最新状态和按持久化事件 ID 分页的记录 |

新运行使用 cycle_id 关联同一周期的遥测、校准、决策和异常。旧实验没有此字段，回放按会话时间关联并保留来源；不能把下一周期观测或未来决策拼接为当时的控制依据。只读查询使用独立 SQLite 连接，页面不会共享控制线程的写连接。

### 8.4 功率预测：从输入接口到实际控制

“功率预测”是独立页面。没有上游数据时显示未接入；软件不会生成一条看似真实的曲线。选择已发布配置后，可查看该配置的资产、控制域和接入契约，粘贴 JSON 或选择本地 JSON 文件，先校验再提交。接口 descriptor 的 example 提供明确标为 synthetic 的试验模板；读取模板或校验输入不会启用前馈。提交后，匹配任务在下个决策周期读取，提交本身不启动任务。

| 输入字段 | 要求与用途 |
|---|---|
| forecast_id | 上游生成的唯一编号；相同编号不能覆盖不同内容，旧发行时间不能覆盖新预测 |
| source.kind / source.name | 来源类型与名称；合成输入 synthetic，实际外部输入 external |
| clock_basis | simulation 为每次运行起点 0 的相对秒；unix 为 Unix 秒，不能混用 |
| issued_at / valid_from / valid_until | 发行时刻、有效区间；不得用未来发行时间，样本必须覆盖有效区间端点 |
| max_age_s | 允许的原始预测年龄，上限 3600 秒；每周期重新检查，物化时间不能延长它 |
| unit | 必须是 W_e，表示电功率；不能把 kW 数值直接填写，也不能用热功率冒充电功率 |
| selection | central 使用 power_w；upper_bound 要求所有样本显式提供上界 |
| entries[].asset_id | 当前配置中的机柜或节点 ID；节点必须归属于机柜，机柜唯一归属控制域 |
| entries[].liquid_fraction | 0–1 的液冷捕热比例，须来自工程依据；不能默认全部 IT 电功率进入液路 |
| entries[].samples | 严格递增且对齐的时间网格，每点含 at / power_w；可有 lower_power_w / upper_power_w |
| job_id（可选） | 更新正在运行的仿真时指定任务，用其相对时间校验；不是修改配置或发设备命令 |

同一机柜只能输入整柜预测，或输入全部已配置节点预测，不能将父机柜和子节点重复计入。节点全覆盖仍不证明未建模的机柜辅助负荷已被包含。当前每包最多 512 个资产、每资产 721 点、合计 50000 点，有效区间不超过 24 小时；HTTP 请求还受 2 MiB 上限约束。缺少某域的任意机柜，该域拒绝前馈并保留反馈，其他覆盖完整且互斥的域仍可使用。

**后台实际链路：**

```text
外部预测系统 / 手动 synthetic 输入
  → 绑定已发布配置的 HTTP 接口
  → 单位、时钟、有效期、资产归属、覆盖与不确定性检查
  → 节点逐点液侧热负荷 = 节点电功率 × 显式液冷分担比例
  → 同一时刻汇总到机柜，再按 served_racks 汇总到独立 CDU 控制域
  → 截取当前时刻至 policy.horizon_s 的区间，取聚合后的液侧峰值
  → Engine 在采集完成后的决策时刻物化预测输入
  → FlowPolicy 使用 max(实测液侧负荷, 有效预测峰值)
  → 需求流量、流量/压差目标、原有限幅限速与安全网关
  → 实际仿真或 Modbus 设备，记录 forecast_usage 与 decision
```

聚合峰值是“同一时刻相加，再取峰值”，不能将各柜在不同时刻的峰值直接相加。内部桥接包为兼容原 FlowPolicy 使用液侧等效功率及比例 1；对外仍分别保留原始电功率和液侧热负荷，不改变原始预测。内部 materialized_at 是此次物化时刻，source_issued_at 始终保留原发行时间。预测不会修改 ThermalPlant 的实际负荷输入。

需求计算沿用 `m_dot = Q_demand / (cp × ΔT_available)` 和原有温差反馈，其中可用温差同时受目标温差及回液软限值约束。压差模式再通过当前水力模型换算成压差，最后经过限幅、限速和命令网关。预测可在负荷到来前提高总流量需求；当前没有自动估计输运延时、选择最优提前量或储冷模型，horizon_s 应依据对象的实测响应设置。

页面明确分开三种状态：聚合预览 ready、实际周期 used/not_used/rejected/absent，以及网关命令是否确认。used 只表示策略采用该预测，不证明冷量已经到位；查看同周期目标、回执、实际温压流与 forecast_id 才能追踪效果。过期、时钟不符、超出热负荷范围或覆盖不足会保留原因；撤回预测只让后续周期恢复反馈，不是停泵或撤销已经下发的目标。

原始输入先归档到工作台状态目录的 `forecast_archive/<config_id>/<sha256>.json`，成功后才激活。SHA-256 对应归档文件实际字节；当前记录、每周期 usage 和 decision 保留 `input_sha256`。同目录的 `id_index.json` 将编号与内容永久绑定，替换、清除及重启后也不能用同一编号提交不同内容。新预测替换或清除当前输入不会删除旧曲线。归档或索引失败、路径异常、已有归档损坏时拒绝激活；恢复持久化输入重新校验，不刷新原始发行时间。页面核对编号和内容哈希，旧无哈希记录明确标注核验边界。归档当前通过文件与审计记录追溯，尚无界面历史版本浏览器。

| API | 行为 |
|---|---|
| GET /api/configs/{id}/forecast/descriptor | 当前发布版本的可用资产、输入契约和 synthetic 示例 |
| POST /api/configs/{id}/forecast/validate | 检查并预览，不保存或启用 |
| POST /api/configs/{id}/forecast | 原子接收预测；现有匹配任务下周期读取，不启动任务 |
| GET /api/configs/{id}/forecast?job_id=... | 已收输入、指定时钟下的聚合预览、各任务实际使用结果 |
| POST /api/configs/{id}/forecast/clear | 撤回当前输入，后续恢复实测反馈 |

以上接口沿用本机 Cookie、同源和 CSRF 边界，外部预测程序应在边缘机本地调用。程序先 GET /api/session 并保存返回 Cookie，再把 csrf_token 放入 POST 的 X-LC-CSRF 头；JSON 中只传预测数据，没有可执行脚本或任意远程下载地址。首版不向互联网开放，也不内置任务平台、GPU 监控或第三方预测模型连接器。

**分配边界：**当前完成的是“负荷归属与各独立 CDU 的总需求计算”。未安装/映射支路执行器时，无法独立指定某个机柜实际获得多少流量。共享水路、共享冷源容量、阀门耦合、N+1 切换和泵组合需要站级协调器；不能把拓扑画得出来当作已实现这些控制。天气输入与冷源能效模型尚未接入本轮算法，无法据此宣称全站能耗最优。

按同一窗口通信步端点功率梯形积分。模型所列冷却包括 5 台 CDU 泵、热水环路泵、冷却塔环路泵和塔风机，不含 IT 或模型外设备，不是全 AIDC 电耗。在线泵耗增加、最高回温略降，控制成功和节能成功分别判断。

### 10.2 跟踪修正结果（新增）

完整数据见 [修正对照报告](../outputs/fmu-validation-20260915/index.html)。两个时域分别比较，不把长阶段的稳态效果当作快速负荷效果。

| 指标 | 原条件：每 10 min 变负荷 | 长阶段：每 60 min 变负荷 |
|---|---|---|
| 原在线算法 → 修正算法，流量 MAE | 2.009 → 1.745 kg/s，改善 13.1% | 1.279 → 0.734 kg/s，改善 42.7% |
| 各阶段末 10 min 流量 MAE | 等于全程指标，阶段本身仅 10 min | 0.599 → 0.030 kg/s |
| 原在线算法 → 修正算法，CDU 1 泵电量 | 3.423 → 3.952 kWh，增加 15.5% | 12.972 → 12.552 kWh，减少 3.2% |
| 相对固定压差基线 | 仍耗电更多 | 仍耗电更多 |
| 修正算法在线晋升 | 0 次 | 0 次 |

根因包括初始 gain 偏大、水力模型斜率不符、约 40 min 的本地 t90、每分钟 3 kPa 的外部限速。低负荷需求约 10.4 kg/s，还低于最低允许压差对应的模型流量约 11.14 kg/s，因此即使无限等待也不能在当前限值内完全满足该目标。新增反馈没有修改这些设备限制；不声称已解决快速跟踪或实现系统节能。

### 10.3 产品指标如何验收

| 指标 | 口径 | 当前缺口 |
|---|---|---|
| 通信执行 | 采集成功率、端到端/确认时延、拒绝/不确定次数、实际跟踪误差 | 有日志和测试，缺 OEM 台架/现场长期分布 |
| 热运行 | 关键测点峰值、越限时长、阶跃恢复；机柜需关键温度和最小流量 | 只覆盖模型/配置守护量，无芯片安全验证 |
| 校准 | 有效样本、冻结原因、保留误差、参数幅度、跨工况表现 | 有候选/晋升记录，缺独立现场数据 |
| 能效 | 同负荷、环境、边界、服务水平下积分电量，明确计量与对照 | 合成部分改善；本轮 FMU 无改善；无现场承诺 |
| 可靠性 | 失联接管、重复写、重启对账、磁盘容量、长期稳定性 | 部分故障自动测试；高可用、自动对账、容量治理未完成 |

不从厂家宣传复制节能率、毫秒响应或温控精度作为已达指标。现场目标由设备能力、传感器、工程限值及验证条件确定。

### 11.1 调用链与扩展原则

```text
CLI → load_scene / validate_scene → operations.run
  → 锁定设备端点和输出目录
  → Adapter + Engine(ControlService, FlowPolicy, Store)
  → 周期 tick
      读取 Snapshot → 保存 telemetry → heartbeat / 运行检查
      → observe / 校准记录 → propose / 标准请求
      → submit / 网关 → 先写审计 → 设备写入和回读
      → 保存 decision
  → finally: close / 尝试交还本地 → 关闭数据库 → 报告
```

新增协议实现 describe、read、write、心跳和释放语义，保留网关。新增模型/优化器通过标准观测/请求接入，不绕过审计，不修改保护限值。新增字段必须有执行语义和校验。

## 12. 数据、故障与恢复

SQLite 使用 WAL/FULL，事件含 session、telemetry、decision、calibration、model、fault、forecast_input_error、forecast_usage。commands.jsonl 保存模式、dispatch_intent、回执、交接。写意图先落盘同步，再发设备命令；采样存储失败不静默丢弃。

| 状态/原因 | 含义与处理 |
|---|---|
| setpoint_confirmed | 目标回读一致，继续观察实际响应 |
| shadow | 未执行候选，不计算实际节能 |
| control_owner_mismatch / device_mode_mismatch | 模式/归属不允许，核对交接，不伪改枚举 |
| temperature_protection_not_verified | 缺所需防凝露证据/露点条件，维持温度写入禁用 |
| minimum_interval_not_met | 动作太密，等下一周期，不删除保护 |
| invalid_guard_observation / stale_source | 守护量/源刷新异常，检查采样链路 |
| uncertain / restart_pending_intent | 结果未知，禁止自动重发，核对设备并保留审计 |
| handoff_unconfirmed | 未确认本地接管，核对设备模式和看门狗 |
| exit_code=2 | 本次故障，查看 fault 和命令日志再决定恢复 |

同命令 ID 不重复写，冲突 ID 拒绝。未完成意图、不确定动作或损坏审计阻止重启自动控制。先核对设备目标/模式/接管，保存处置证据及原日志，确认交接后建新会话；**不要删审计解锁。** 没有自动对账/回滚向导，不应无条件重启为 control。

没有自动留存、备份、磁盘容量治理或高可用。长期边缘运行前需补齐；学习模型不替代设备保护。
